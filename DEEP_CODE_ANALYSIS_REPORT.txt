# DEEP CODE ANALYSIS REPORT

## 1. Overview

This analysis examines the conditional UI rendering implementations for business categories in two key screens: **MyBusinessPosterPlayerScreen.tsx** (handling "Event Planner" category) and **IndustryCategoryScreen.tsx** (handling "Software Company" category). The investigation reveals distinct architectural approaches for category-specific UI rendering, with significant differences in data handling, filtering mechanisms, and component organization.

## 2. PosterPlayerScreen - Rendering Flow

### Business Category Detection
The screen receives business category data through a multi-layered approach:
- **Primary Source**: `useBusinessProfile()` context hook provides `selectedBusinessProfile`
- **Category Resolution**: Uses fallback hierarchy: `subCategory || subcategory || category`
- **Data Flow**: BusinessProfileContext -> MyBusinessPosterPlayerScreen -> conditional rendering

### Rendering Architecture
The screen follows a **conditional rendering pattern** with early returns:
1. **No Category Check**: Returns fallback UI if no business category exists
2. **Software Company Redirect**: Routes to IndustryCategoryScreen for "software company" subcategory
3. **Standard Flow**: Continues with normal poster player UI for other categories

## 3. Event Planner Logic Breakdown

### Category Detection Logic
```typescript
const isEventPlannerCategory = useMemo(() => {
  const category = (businessCategory || '').trim().toLowerCase();
  const eventPlannerVariations = [
    'event planners', 'event planner', 'event-planners', 
    'event-planner', 'eventplanners', 'eventplanner'
  ];
  return eventPlannerVariations.some(variation => category.includes(variation));
}, [businessCategory]);
```

### Conditional UI Components
**Service Filter Buttons** (Lines 942-991):
- **Trigger**: `{isEventPlannerCategory && (...)}` 
- **Buttons**: Generator, Decorators, Sound, Mandap
- **Data Source**: Static array with keyword mapping
- **State Management**: `selectedServiceFilter` + `serviceFilterTemplates`

### Data Filtering Mechanism
**Tag-Based Filtering**:
- **Keywords**: `serviceFilterKeywords` object maps filter keys to tag arrays
- **Filter Logic**: Templates filtered by matching tags against keywords
- **Cache Strategy**: EventPlanner templates cached separately in `serviceFilterTemplates['eventplanner']`

### API Integration
**Specialized Fetching**:
- **Dedicated Function**: `fetchEventPlannerTemplates()` 
- **API Endpoint**: `businessCategoryPostersApi.getPostersByCategory('eventplanner', 500)`
- **Template Enhancement**: Adds `previewUrl` field for high-quality images

## 7. Key Differences

### Architectural Approach
| Aspect | Event Planner (PosterPlayerScreen) | Software Company (IndustryCategoryScreen) |
|--------|-----------------------------------|-------------------------------------------|
| **Category Detection** | Dynamic with variations | Static hardcoded |
| **Screen Organization** | Conditional rendering within single screen | Dedicated separate screen |
| **Data Fetching** | Specialized function with caching | Standard API call |
| **Filter Strategy** | Service-based keyword filtering | Category-based tag matching |

### Data Handling
| Feature | Event Planner | Software Company |
|---------|---------------|------------------|
| **Template Source** | Cached 'eventplanner' category | Direct 'software company' API |
| **Filter Granularity** | 4 service types | 6 category buttons |
| **Cache Strategy** | Separate cache per service filter | Single poster array |
| **State Management** | Complex multi-state | Simple selection state |

### UI Structure
| Component | Event Planner | Software Company |
|-----------|---------------|------------------|
| **Button Layout** | Fixed horizontal | Scrollable horizontal |
| **Visual Feedback** | Loading states per button | Selection highlights |
| **Integration** | Embedded in main screen | Dedicated screen component |
