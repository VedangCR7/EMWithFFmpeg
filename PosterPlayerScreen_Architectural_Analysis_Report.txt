1. POSTER PLAYER SCREEN OVERVIEW
===============================================================================

PosterPlayerScreen is a complex, multi-purpose React Native component that serves as the primary poster viewing and selection interface for the EventMarketers mobile application. It handles four distinct data sources:

• Business Category Posters - Professional templates for specific business categories
• Greeting Category Templates - Social media greeting templates  
• Calendar Posters - Date-specific festival/event posters
• General Posters - Standalone poster viewing with related posters

The screen features sophisticated state management, responsive design, language filtering, and performance optimizations including image preloading and skeleton loading states.

Key Characteristics:
- 4,037 lines of highly complex TypeScript code
- Multi-source data handling with race condition protection
- Advanced responsive design for tablets, phones, and foldable devices
- Sophisticated language detection and filtering system
- Performance-optimized with memoization and lazy loading
- Production-critical component with extensive error handling

- Storage: activeCategoryRef.current = { type: 'business', value: categoryName }

- Source: route.params.greetingCategory (string)
- Storage: activeCategoryRef.current = { type: 'greeting', value: greetingCategory }

- Cache: In-memory serviceFilterTemplates for EventPlanner

Calendar Date:
- Source: route.params.calendarDate (string)
- Storage: activeCategoryRef.current = { type: 'calendar', value: calendarDate }
- API: calendarApi.getPostersByDate(date)
- Cache: No caching, fresh fetch each time

General/Individual Posters:
- Source: route.params.initialPoster + route.params.initialRelatedPosters
- Storage: activeCategoryRef.current = { type: null, value: null }
- API: No API calls, uses provided data
- Cache: N/A

CATEGORY SWITCHING LOGIC:
- Language reset to "All" when switching categories
- User manual language selection tracking reset
- allTemplates cleared immediately to prevent showing old data
- Race condition protection with activeCategoryRef checks

5. LANGUAGE HANDLING
===============================================================================

LANGUAGE SYSTEM ARCHITECTURE:

Supported Languages:
- English (id: 'english')
- Hindi (id: 'hindi') 
- All (id: 'all') - shows all languages

Language Detection Process:
1. Extract keywords from template tags using LANGUAGE_KEYWORDS mapping
2. Check template.languages array (explicit language data)
3. Merge both sources with mergeTemplateLanguages()
4. Prioritize Hindi/Marathi over English when both detected

Language State Management:
- selectedLanguage: Current filter selection
- userManuallySelectedLanguageRef: Tracks manual user selection
- lastAutoDetectedPosterIdRef: Prevents duplicate auto-detection
- Auto-detection skipped when user manually selects language

Language Filtering Logic:
- "All" = No language filtering applied
- Specific language = templateContainsLanguage() function
- Word boundary regex matching prevents false positives
- Templates without language info default to English only

Language Change Triggers:
- Category switching (resets to "All")
- Poster selection via handlePosterSelect()
- Initial poster mount (auto-detection)
- Current poster change for category/calendar modes

6. POSTER LOADING SYSTEM
===============================================================================

API ENDPOINTS:

Business Category:
- Endpoint: /api/mobile/posters/category/{categoryName}?limit={limit}
- Method: businessCategoryPostersApi.getPostersByCategory()
- Limit: 1000 for "My Business", configurable via posterLimit param
- Cache: Cleared for "My Business" to ensure fresh data

Greeting Category:
- Primary: greetingTemplatesService.getTemplates({ category, limit })
- Search: greetingTemplatesService.searchTemplates(term, undefined, limit)
- Variations: Multiple searches with normalized category terms
- Progressive loading: 50 initial, 200 background after render
- Cache: In-memory with serviceFilterTemplates

Calendar Posters:
- Endpoint: calendarApi.getPostersByDate(date)
- Method: Direct API call
- Cache: No caching implemented

CACHING LOGIC:
- Image preloading with preloadedImagesRef Set
- Template caching in serviceFilterTemplates for EventPlanner
- API response caching handled by service layers
- Memory cleanup on unmount

SKELETON LOADING:
- SkeletonItem component with shimmer animation
- Shows during isBusinessCategoryLoading or isGreetingCategoryLoading
- 6 skeleton items displayed in grid layout
- Animated.Value with 1000ms duration loop

ERROR HANDLING:
- Try-catch blocks around all API calls
- Graceful fallbacks for missing data
- Console logging for debugging
- Loading state management for UI feedback

14. RISK ANALYSIS
===============================================================================

POTENTIAL RISKS & MITIGATION STRATEGIES:

1. SHARED STATE CONFLICTS
   - Risk: Language state leakage between PosterPlayerScreen and MyBusinessPosterPlayerScreen
   - Mitigation: Use independent language state refs (userManuallySelectedLanguageRef, etc.)
   - Impact: High - Could cause unexpected language switching

2. CACHING COLLISIONS
   - Risk: Image preloading cache conflicts between screens
   - Mitigation: Use separate cache keys or clear cache on screen unmount
   - Impact: Medium - Could cause memory issues or stale images

3. NAVIGATION CONFUSION
   - Risk: Back navigation going to wrong screen
   - Mitigation: Explicit originScreen handling for MyBusiness flow
   - Impact: High - Could break user journey

4. API RATE LIMITING
   - Risk: Both screens calling same business category API simultaneously
   - Mitigation: Share API cache or implement request deduplication
   - Impact: Medium - Could trigger rate limiting

5. BUSINESS PROFILE CONTEXT CONFLICTS
   - Risk: Global business profile changes affecting both screens
   - Mitigation: Pass business profile as navigation param instead of relying on context
   - Impact: High - Could show wrong business posters

6. MEMORY LEAKS
   - Risk: Component not properly cleaning up refs and listeners
   - Mitigation: Ensure all useEffect cleanup functions are preserved
   - Impact: Medium - Could cause performance degradation

7. RESPONSIVE DESIGN BREAKS
   - Risk: New screen not matching exact layout of original
   - Mitigation: Copy all styling and responsive logic exactly
   - Impact: Medium - Could cause UI inconsistency

8. LANGUAGE FILTERING BUGS
   - Risk: Language detection not working for business-only flow
   - Mitigation: Test language detection with business category posters
   - Impact: High - Could break core functionality
