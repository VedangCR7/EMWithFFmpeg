========================

OBJECTIVE:
Understand the current implementation structure, data flow, category handling, and UI behavior of both screens without suggesting changes.

---

1. OVERALL ARCHITECTURE

Both screens follow a similar structural pattern:

* Single screen handles:
  - Category selection
  - Poster filtering
  - Poster rendering
  - User interaction (selection, navigation)

* No strict separation between:
  - UI layer
  - Business logic
  - Data transformation

This results in tightly coupled logic inside screen components.

---

2. CATEGORY HANDLING

2.1 Category Source

* Categories are not dynamically derived from a structured hierarchy
* They are introduced via:
  - Static arrays (languages array with hardcoded language objects)
  - Inline JSX buttons (service filter buttons for Event Planners)
  - Hardcoded string values (businessCategory from context)

2.2 Category Representation

* Categories are represented as plain strings:
  e.g. 'AI', 'Website Development', 'hindi', 'english', 'all'

* Some categories use unique identifiers (language.id) but not consistently across all category types

2.3 Category Selection Flow

* User clicks a button (TouchableOpacity with LinearGradient styling)
* A state variable is updated (selectedLanguage, selectedServiceFilter)
* UI re-renders based on this state value
* Poster filtering logic is re-executed

3. UI STRUCTURE

3.1 Category UI

* Language Filter: Horizontal scrollable button list
  - Rendered using .map() on languages array
  - Conditional styling based on selectedLanguage state
  - LinearGradient backgrounds for selected states

* Service Filter: Grid-based button layout (Event Planners only)
  - Hardcoded filter keys: ['generator', 'decorators', 'sound', 'mandap']
  - Conditional rendering based on isEventPlannerCategory
  - Loading states handled per filter

3.2 Poster Display

* Posters are displayed using:
  - FlatList with numColumns for grid layout
  - Custom renderItem function (renderRelatedPoster)
  - Skeleton loading states during data fetch

* Key rendering characteristics:
  - Responsive numColumns based on screen width
  - Performance optimizations (removeClippedSubviews, maxToRenderPerBatch)
  - Custom card dimensions calculated dynamically

3.3 Interaction Layer

* Poster selection triggers:
  - setSelectedPoster() state update
  - Navigation to poster editor (navigateToPosterEditor)
  - Console logging for debugging

* Interaction handlers are defined within the same file (handlePosterSelect)

4. DATA FLOW

4.1 Poster Data Source

* Posters are fetched from:
  - businessCategoryPostersApi.getPostersByCategory()
  - API response structure: { success: boolean, data: { posters: BusinessCategoryPoster[] } }

4.2 Data Transformation

* BusinessCategoryPoster objects are transformed to Template format:
  - id: poster.id
  - name: poster.title || 'Business Poster'
  - thumbnail: poster.thumbnail || poster.imageUrl
  - category: poster.category || businessCategory
  - languages: poster.tags || []
  - tags: poster.tags || []

* Filtering happens at screen level using:
  - selectedLanguage state
  - selectedServiceFilter state (for Event Planners)
  - Conditional logic based on category type

4.3 Flow Sequence

API Call (getPostersByCategory) -> Data Transformation -> State Update (setPosters) -> Filtering Logic -> FlatList Render

* No intermediate abstraction layer exists
* Filtering logic is embedded in useMemo hooks

---

5. STATE MANAGEMENT

5.1 Local State Usage

* useState is used for:
  - posters: Template[] (poster data)
  - loading: boolean (loading state)
  - selectedPoster: Template | null (currently selected poster)
  - selectedLanguage: 'all' | 'english' | 'hindi' (language filter)
  - selectedServiceFilter: string | null (service filter for Event Planners)
  - serviceFilterTemplates: Record<string, Template[]> (cached filtered templates)
  - isLoadingServiceFilter: Record<string, boolean> (loading states per service)

5.2 State Dependency

* Poster rendering is directly tied to selectedLanguage and selectedServiceFilter
* Any change in filters triggers re-execution of filtering logic
* Service filter templates are cached to avoid repeated API calls

5.3 Lack of Hierarchy

* Only one level of filtering state:
  - No parent-child category relationship
  - No grouped state for different category types
  - Language and service filters are independent

* Logic is distributed across:

6.2 Conditional Rendering

Example patterns:

9.2 Filtering Cost
