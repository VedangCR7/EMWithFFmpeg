2. LOCK CARD LOGIC ANALYSIS
===========================

Lock Condition Definition:
--------------------------
Primary lock condition: `const isLocked = !isEffectivelyActive`
Where `isEffectivelyActive = isActive && !isPendingActivation`

Lock Status Determination:
--------------------------
1. Backend Status: `item?.subscriptionStatus?.toUpperCase() === "ACTIVE"`
2. Processing Status: `item?.subscriptionStatus?.toUpperCase() === "PROCESSING"`
3. Pending Activation: `isActivationPending(item.id)` from context
4. Final Lock State: Combined evaluation of backend status and pending state

Conditional Rendering for Locked vs Active:
-------------------------------------------
Locked UI renders when `isLocked = true`:
- Full-screen overlay with semi-transparent background
- Lock badge centered in overlay
- Different content based on specific status:
  * PROCESSING: Hourglass icon + "Payment is processing" message
  * PENDING ACTIVATION: Hourglass icon + "Activation in progress" message  
  * INACTIVE: Lock icon + "Subscription Required" + Activate button

Active UI renders when `isLocked = false`:
- No overlay
- Full card interactivity
- All action buttons enabled

User Interaction Restrictions:
-----------------------------
- TouchableOpacity disabled={isLocked} on main card
- Edit button disabled={isLocked}
- Delete button disabled={isLocked}
- Card press handler blocked for locked profiles
- Only "Activate Now" button remains functional for inactive profiles

4. DATA FLOW & STATE MANAGEMENT
===============================

Data Source:
-----------
- Primary: `businessProfileService.getUserBusinessProfiles(userId)` API call
- Fallback: Empty array if API fails
- Mock data available for development (not used in production)

State Storage:
-------------
- Local state: `profiles` useState hook
- Subscription context: `useSubscription()` hook
- Business profile context: `useBusinessProfile()` hook
- Processing state: `processingProfiles` Set for UI loading states

Active/Inactive Status Storage:
-------------------------------
- Backend: `subscriptionStatus` field in profile object
- Context: `getBusinessProfileSubscription(profileId)` 
- Activation pending: `isActivationPending(profileId)` from context
- Processing: `processingProfiles` Set for payment processing

State Update Flow:
-----------------
1. API call updates profiles state
2. Subscription context updates via polling
3. UI re-renders when state changes
4. BusinessCard memoization controls re-render frequency
5. Image refresh key forces logo re-rendering

Centralized vs Per-Card Control:
-------------------------------
- Lock behavior: Centralized via subscriptionStatus field
- Activation pending: Context-based (centralized)
- Processing state: Per-card via Set data structure
- UI updates: Automatic through React re-rendering

5. ACTION HANDLING ANALYSIS
===========================

Available Actions on Business Cards:
-----------------------------------
1. View/Select: `handleProfileSelect()` - Main card press
2. Edit: `handleEditProfile()` - Edit button press
3. Delete: `handleDeleteProfile()` - Delete button press  
4. Activate: `initiatePaymentForProfile()` - Payment flow initiation

Action Button Conditional Rendering:
-----------------------------------
Edit Button:
- Always rendered visually
- Disabled when `isLocked = true`
- Color changes to gray when disabled

Delete Button:
- Always rendered visually
- Disabled when `isLocked = true`
- Color changes to gray when disabled
- Handler exists but blocked by disabled state

Activate Button:
- Only rendered for inactive profiles (not processing/pending)
- Located inside lock overlay
- Triggers payment flow

Delete Action on Locked Profiles:
--------------------------------
- Delete button exists but is disabled
- Delete handler `handleDeleteProfile()` is fully implemented
- Deletion is blocked via `disabled={isLocked}` prop
- No separate delete restriction logic beyond disabled state
