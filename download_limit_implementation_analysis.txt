1. CURRENT DOWNLOAD FLOW
------------------------

Step-by-step explanation of how a download currently works in the system:

1. User initiates download from mobile app (PosterPreviewScreen.tsx)
2. Mobile app calls downloadPoster() function in PosterPreviewScreen.tsx (line 352)
3. Download saves image to device gallery using CameraRoll.save()
4. Mobile app calls trackPosterDownload() from downloadHelper.ts (line 418)
5. downloadHelper.ts calls downloadTrackingService.trackDownload() (line 34)
6. downloadTrackingService makes POST request to /api/mobile/downloads/track
7. Backend downloads.ts route handles the request (line 14)
8. Backend validates user exists and creates MobileDownload record (line 170)
9. Backend returns success response with download details
10. Mobile app shows success message to user

Key Points:
- Download tracking is separate from actual file download
- Backend stores download records in MobileDownload table
- No current limit checking exists
- Duplicate prevention is implemented (lines 77-119 in downloads.ts)

3. DATABASE ANALYSIS
--------------------

Relevant tables:
- MobileDownload - Stores all download records
  - id, mobileUserId, businessProfileId, resourceType, resourceId, fileUrl, downloadedAt, createdAt
  - Already has mobileUserId for user association
  - No download limit fields currently

- MobileSubscription - User subscription records
  - Links to mobile_subscription_plans via planId
  - Has status, startDate, endDate for active period checking

- mobile_subscription_plans - Subscription plan definitions
  - id, name, price, period, features, isActive
  - No download limit fields currently

- MobileUser - User accounts
  - Links to MobileDownload and MobileSubscription

Required schema changes:
1. Add download limit fields to mobile_subscription_plans:
   - dailyDownloadLimit (Int, nullable)
   - monthlyDownloadLimit (Int, nullable)

2. Add download tracking fields to MobileUser (optional):
   - dailyDownloadCount (Int, default 0)
   - monthlyDownloadCount (Int, default 0)
   - lastDownloadResetDate (DateTime)

3. Add indexes for performance:
   - Index on MobileDownload.mobileUserId + downloadedAt for counting
   - Index on MobileSubscription.mobileUserId + status + endDate

7. RISKS / EDGE CASES
-----------------------

Concurrency issues:
- Multiple simultaneous downloads could exceed limits
- Solution: Use database transactions or atomic counters

Multiple download attempts:
- Rapid clicking could bypass limits
- Solution: Add rate limiting and duplicate prevention (already exists)

Caching problems:
- Download count caching could show stale limits
- Solution: Use real-time database queries for limit checking

Timezone issues for daily limits:
- Users in different timezones could have different reset times
- Solution: Use UTC timezone for all date calculations

Performance concerns:
- Counting downloads for each request could be slow
- Solution: Add cached counters and optimize database queries

Edge cases:
- What happens when subscription expires during download?
- How to handle plan changes with different limits?
- How to handle promotional periods with unlimited downloads?
